# Interview talking points (first person)

Plain-language notes so I can explain every part of OutbreakScope. Numbers are from my own test runs.

1. **What an SEIR model is and what R0 means.** I sort people into boxes: Susceptible, Exposed (infected but not yet infectious), Infectious, Recovered. Each day people flow between boxes at rates set by the disease. R0 is the average number of people one infectious person infects in a fully susceptible population. If R0 is above 1 the outbreak grows, below 1 it dies out. A related number, R_eff, is R0 times the share still susceptible times how much contact has been cut, so it falls as people get immune or as an intervention starts. Herd immunity threshold is 1 - 1/R0: above that immune share, each case infects fewer than one other.

2. **How RK4 works and why I wrote it myself.** The equations give the speed of change right now, not the curve, so the computer takes small steps in time. Euler's method walks along the current slope, which drifts. RK4 measures the slope four times per step (start, twice in the middle, end) and blends them with weights 1, 2, 2, 1 over 6, so halving the step shrinks the error about 16 times. I wrote it myself so I could prove it right and explain it: I measured the order as about 4.0 and made the integrator land exactly on the days where interventions start and stop, because the rates jump there.

3. **How I proved the solver is right.** Four independent ways. Conservation (everyone is always somewhere, S+E+I+R+V = N within 1e-9 of N). Convergence order (halving the step cuts the error by about 16). Analytical formulas (the final size matches the root of z = 1 - exp(-R0 z) to 1e-6; the early growth rate matches an eigenvalue formula I derived). And SciPy: nine reference trajectories agree to 1.6e-9 of the population, and three scenarios exported from the app and re-solved by a separate Python script agree to 8e-10. A test also caught a claim I had wrong: in SEIR it is the peak of E+I, not I, that sits where R_eff = 1.

4. **Why stochastic models matter for small outbreaks.** The ODE gives one smooth curve, but when only a few people are infected, luck decides whether it takes off. With R0 = 2 and one starting case, theory says about half of outbreaks fizzle out (1/R0). My simulations gave 0.502, and 0.249 for two starting cases (theory 0.25). I used the exact Gillespie algorithm for small populations and cheaper binomial steps for large ones, and made every run reproducible from a displayed seed, independent of how many workers share the work.

5. **What "identifiability" means, with an example from my own app.** It asks whether the data can pin a parameter down. If I only have data from the early exponential phase, the counts look like (reporting fraction) x (initial infected) x e^(rt), so the data fix the growth rate and the product of the other two, but not each alone. My app showed their posterior correlation as -0.89 and printed a warning. With full-wave data, R0 and the initial number infected trade off (-0.91 to -0.98): a faster epidemic started by fewer people peaks at the same time. That is why fixing parameters from outside knowledge is the honest default.

6. **What MCMC and R-hat are in plain English.** MCMC explores which parameter values are plausible by taking a random walk that spends more time where the model explains the data better. R-hat is a check that independent runs of that walk agree with each other; near 1.00 means they do, and I require below 1.05. Effective sample size says how many independent draws a correlated chain is worth (I require 200). If they fail the app says NOT converged and hides the fitted curve, because a confident-looking result from a sampler that has not settled would be misleading.

7. **Why heavy computation lives in workers.** Stochastic ensembles and fits take seconds; on the main thread they would freeze the interface. Workers run them in parallel with progress bars and a Cancel button (cancelling terminates the worker). A 1000-run ensemble at one million people took about 0.4 seconds across four workers, and a full fit about 5 seconds, with the worst main-thread stall I measured at 153 ms.

8. **Why typed messages and zod validation.** TypeScript types disappear when the program runs, so anything from outside gets checked at run time: files I read (CSV after parsing, scenario JSON, the dataset manifest) and every request that crosses from the page to the main process. Worker messages are TypeScript unions, so the compiler checks both ends of every message. That caught real mistakes and means a corrupted or newer-version file gives a friendly error, not a crash.

9. **The security design.** The page cannot touch the computer: sandbox on, Node off, strict Content-Security-Policy, no network (and I cancel any request at the session level). It only talks to the main process through four functions I expose, and the main process re-checks everything: file size and type, file text-only, and only https links to a short allowlist ever open in the browser. Tests probe all of that, including path traversal on my custom `app://` protocol, and a test scans the source for banned things such as `fetch`, `eval` and `Math.random`.

10. **Tradeoffs and limitations.** The model is deliberately simple (everyone mixes equally, one wave, constant rates except my interventions), so it is for teaching, not forecasting. On the real Utah hospital data it fits poorly (only 51% and 69% of points fall in the model's own 95% band), and the app tells the user that instead of showing a tight but misleading interval. Reported counts are not infections; one fitted reporting fraction absorbs all of that. Installers are unsigned, and I only tested macOS locally; Linux and Windows are verified by CI only.
